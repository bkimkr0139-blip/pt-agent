# 로컬 LLM 모델 교체 평가 시스템 — 설계·운영 문서

> v1.0 · 2026-10-04 · PPT 발표 에이전트 (Mac Studio M3 Ultra 96GB)
> 대상: 로컬 LLM · STT · TTS 모델의 "최신 모델 조사 → 실측 평가 → 무중단 시험 적용 → 승인/롤백" 전 과정

---

## 1. 개요와 목적

로컬 모델 생태계는 매일 바뀐다(qwen3 계열만도 매일 신규 빌드·파인튜가 업로드된다). 그런데 모델 교체는 전통적으로 (1) 소문이나 감으로 후보를 고르고 (2) 교체 후 문제가 생기면 손으로 되돌리는, 되돌릴 수 없는 단방향 작업이었다. 이 시스템은 그 과정을 **조사 → 실측 → 시험 → 검증 → 승인**의 되돌릴 수 있는 파이프라인으로 바꾼다.

핵심 질문 세 개에 데이터로 답한다:

1. **지금보다 나은 모델이 나왔나?** — HuggingFace 최신 조사 + 메타데이터 1차 선별
2. **실제로 나은가?** — 동일 태스크 실측 벤치마크(속도·품질·언어 올바름)
3. **우리 서비스에서도 나은가?** — 실제 트래픽 시험 운영 + 무결루프가 수집한 운영 로그 검증

## 2. 시스템 체계

### 2.1 구성 모듈

| 모듈 | 역할 |
|---|---|
| `model_eval.js` | 평가 엔진 — 후보 조사, 벤치마크 실행기, 판정, 시험 전환, 검증 보고서 집계 |
| `eval_page.js` | 관리자 UI — 탭형 조사 표, div 쌍봉 차트, 판정 카드, 시험 승인/롤백 버튼 |
| `eval/registry.json` | 스택별 "현재 모델" 단일 진실원 (승인 시 갱신) |
| `eval/discovery.json` | 조사 캐시(30분) — HF API 결과 + 파생 정보 |
| `eval/trial.json` | 시험 상태 — 후보 명세·시작시각·백업·승인/롤백 이력 |
| `eval/results/*.json` | 벤치마크 리포트 원본 (실측 값 영구 보존) |

### 2.2 연동 관계

```
                    ┌─ HuggingFace API (후보 조사)
model_eval.js ──────┼─ ollama :11434 (LLM 벤치 — 현재/후보 동일 태스크)
                    ├─ STT :8323 / :8782 (A/B 벤치)
                    └─ TTS 프록시 :8321 (5문장 실측)
       │
       ├─ server.js proxyToN8n ─── trial.json(status=trial) 읽어 body.model 주입 → n8n → ollama
       ├─ tts_policy.json(tts_model/voice) ─── 프록시가 전 트래픽에 강제 적용(mtime 즉시 반영)
       └─ 검증 보고서 ◄── pt-agent.log 접근지연 + mlx-tts-proxy.log 성공/실패 + issues.jsonl(무결루프)
```

### 2.3 5단계 파이프라인

```
①조사(HF 최신순+피드백 등급) → ②벤치마크(전부 실측) → ③비교 차트·자동 판정
   → ④시험 운영(실제 발표 트래픽 전환, 즉시 롤백 가능) → ⑤무결루프 검증 → ✅승인 확정 / ↩️롤백
```

## 3. 세부 기능

### 3.1 후보 조사 (1차 선별)
- **소스**: HuggingFace API, 스택별 질의 세트(LLM=gguf 필터, STT, TTS)를 최신순 조회, 다운로드 10+ 필터로 잡동사니 파인튜 제거, 30분 캐시.
- **행 강화**(모델명·태그에서 자동 추출):
  - 특징 — 파라미터 수, 양자화(Q4/Q5…), 계열(qwen3/llama/gemma/exaone…), 런타임(MLX/ONNX), 증류·검열제거⚠ 플래그
  - 시장 피드백 — 다운로드/좋아요 실수치 → 🟢검증됨(1k+)/🔵주목(100+)/⚪신규 등급
  - 기대 개선(추정) — 규칙 기반 문구: "경량 — 속도 대폭 기대, 품질 하락 위험 · 현행 qwen3 계열(호환성 양호)" 등. **추정임을 명시**하고 실제 근거는 벤치마크로 안내.

### 3.2 벤치마크 (전부 실측 — 가공 수치 없음)
- **LLM — 발표 도메인 5태스크**: ①발표 대본 생성 ②근거형 QA ③지시 이행(목록화) ④**언어 올바름(한국어 고정)** ⑤요약(길이 적정성). 스트리밍 실측으로 TTFT(첫 응답), tok/s(최종 청크 통계), 한국어 비율·중국어 오염률(**문자 기준 분모** — 숫자·문장부호가 분모에 끼면 "1. 속도." 같은 완벽한 지시 이행이 오탐되는 문제를 구조적으로 차단), 길이 적정성.
- **언어 올바름 게이트**: 후보가 하나라도 중국어 오염(cjk≥1%) 또는 한국어 이탈이면 **무조건 "비권장"** — 실제로 qwen2.5:14b가 발표 초안을 중국어로 쓰던 결함 클래스의 재발을 벤치 단계에서 차단.
- **STT — A/B**: bench 샘플을 두 라이브 엔드포인트(8323 Qwen3-ASR vs 8782 whisper)에 던져 RTF(실시간 계수)·처리시간·빈 결과 실측.
- **TTS**: 5개 고정 문장(한국어+영어 약어 포함)을 실제 프록시 경로로 생성 — 성공률, 지연, 자연 길이 비율(4~7자/초, WAV 파싱 실측).

### 3.3 비교 차트와 자동 판정
- 현재 vs 후보 **쌍봉 차트**(div 기반 — SVG 텍스트 왜곡 없음) + 변화율 배지("낮을수록 좋은" 지표는 방향 자동 보정: TTFT −10.1%는 좋음, tok/s −10%는 나쁨).
- **자동 판정**: 언어게이트 실패→비권장, 태스크 통과 우위+속도 유지→교체 권장, TTS 전륜 통과+지연 허용범위→시험 권장, 그 외 보류.
- **사용자 관점 불릿**: 수치를 체감 언어로 번역("첫 응답까지 −10% (129→116ms)", "실패 시 브라우저 폴백 목소리 노출 감소" 등).

### 3.4 시험 운영 (무수정 무중단 전환)
| 스택 | 전환 메커니즘 | 롤백 |
|---|---|---|
| LLM | server.js가 trial.json을 읽어 n8n 프록시 바디에 model 주입 — n8n 게이트웨이가 `b.model`을 존중하므로 **n8n·클라이언트 무수정** | trial.json 반영 즉시 복원(요청 단위) |
| TTS | tts_policy.json에 tts_model/tts_voice 기록 → 프록시가 **모든 요청에 강제 적용**(mtime 감지, 재시작 불필요) | 백업값 복원+버전 증가(즉시) |
| STT | 자동 전환 없음 — 발표 QA는 브라우저 Web Speech API, 8323은 n8n 서비스용. 전환은 n8n koen_local_stt 대상 수동 변경(문서화) | — |

- 시험 시작 시 이전 정책값을 trial.json에 백업. 롤백은 백업 복원+정책 버전 증가 — 서비스 재시작 0회.

### 3.5 검증 보고서 (무결루프 연동 — 최종 판단 근거)
벤치마크는 "잠재력"을, 검증 보고서는 "실전 성적"을 담당한다. 시험창 vs **직전 동일 길이 창**의 실제 운영 데이터:

- TTS: 문장 성공 수, 평균 생성 시간, 분할 자동 구출(SPLIT-OK), 최종 실패(폴백 위험) — 프록시 타임스탬프 로그에서 집계
- LLM: 호출 수, 평균 응답 시간, 오류 응답 — 서버 접근 로그에서 집계
- 시험 중 무결루프가 잡은 이슈(issues.jsonl) 병기 — 새 실패 시그니처가 없으면 "무결루프 이슈 없음"으로 명시

사람이 조작할 수 없는 로그만으로 판단하며, 관리자는 이 화면에서 **최종 승인(전환 확정, registry 갱신)** 또는 **롤백**을 누른다.

## 4. 특장점

1. **무수정 전환** — 클라이언트, n8n 워크플로우, 프록시 코드 어디도 고치지 않고 프로덕션 트래픽을 모델 간에 스위칭. 전환이 어려운 시스템은 시험 자체를 생략하게 되는데, 이 시스템은 전환 비용이 0이라 시험을 생략할 명분이 없다.
2. **실측 전용, 조작 불가** — 판정 근거가 전부 자동 수집 로그. "좋아 보이는 데모"가 아니라 숫자가 결정한다.
3. **언어 올바름 게이트** — 한국어 서비스 특화. 모델 교체로 생기는 최악의 장애(다른 언어로 답변)를 벤치 단계에서 원천 차단.
4. **되돌릴 수 있는 교체** — 시험→검증→승인 게이트와 즉시 롤백. 교체가 이제 단방향 위험이 아니라 실험이다.
5. **폐루프와의 결합** — 무결루프(정책 자동조정)가 모델 "내부"의 품질을 스스로 보정하는 동안, 이 시스템이 모델 "바깥"(어떤 모델을 쓸까)의 생애주기를 관리 — 두 층이 합쳐져 시스템이 시간이 지날수록 저절로 나아진다.
6. **안전장치 내장** — 벤치마크 단일 실행 락(중복 실행 차단), GPU 경합 경고(발표 중 실행 금지), 후보 없는 실행 방지, 시험 중복 차단.

## 5. 타 시스템 적용 방안

이 시스템의 본질은 모듈이 아니라 **패턴**이다: "관문 프록시 + 정책 파일 + 시험 스위칭 + 로그 검증".

### 5.1 적용 조건 체크리스트
- [ ] **전환 추상화 계층** — 트래픽이 반드시 하나의 관문(프록시/게이트웨이/의존성 주입점)을 지나는가? 지나지 않으면 관문을 먼저 만든다.
- [ ] **관문이 대상을 파라미터로 받는가** — 모델/엔드포인트가 하드코딩이 아니라 요청 바디·정책 파일로 결정되는가? (본 시스템: n8n 게이트웨이의 `b.model||기본값` 패턴)
- [ ] **실패 시그니처 로그** — 실패가 사유와 함께 타임스탬프로 남는가? 없으면 무결루프의 시그니처 스캐너부터 심는다.
- [ ] **동일 태스크 벤치 가능** — 현재와 후보를 같은 입력으로 비교할 수운 표준 태스크 세트를 만들 수 있는가?
- [ ] **백업·롤백 경로** — 이전 설정을 저장하고 즉시 복원할 수 있는가?

### 5.2 확장 예시
- **다른 모델 스택**: STT(whisper→신규 ASR), 임베딩(nomic→신규), 이미지 생성 모델 — `model_eval.js`의 스택 레지스트리에 엔드포인트+벤치 태스크만 추가하면 동일 파이프라인이 동작한다. STT A/B가 그 선례(두 라이브 엔드포인트를 레지스트리에 등록).
- **다른 서비스**: 같은 4계층(관문/정책/벤치/검증)을 사내 다른 에이전트에 복제. 관문만 있다면 LLM이 아니라 검색 엔진, OCR, 분류기에도 동일하게 적용된다.
- **자동화 단계 확장**: 지금은 관리자가 승인하지만, 검증 보고서의 임계값(예: 성공률·지연이 기준선 대비 열위 없음)을 충족하면 자동 승인하는 단계를 얹을 수 있다 — 무결루프의 자동 패치와 같은 철학.

### 5.3 적용 시 주의
- 벤치마크는 실제 GPU를 점유 — 서비스 사용 중 실행 금지(단일 실행 락과 경고 UI로 방어).
- "기대 개선"은 메타데이터 추정일 뿐 — 승인 판단은 반드시 벤치마크+시험 검증 데이터로.
- 신규 업로드 모델은 커뮤니티 검증이 부족하다(피드백 등급 참조) — 프로덕션 승인은 "검증됨" 등급 이상을 기본 권장.

## 6. 운영 절차 (요약)

```
1. 관리자 페이지 → 🔄 모델 교체 평가
2. [🔍 조사 실행] → 탭에서 후보 1차 선별 (특징·피드백·기대 개선 참고)
3. 미설치 LLM이면 터미널: ollama pull <모델>
4. [벤치마크] → 차트·판정·사용자 관점 확인
5. 유망하면 [⏱ 시험 운영 시작] → 실제 발표로 며칠 운영
6. [📊 검증 보고서] → 운영 데이터 비교 + 무결루프 이슈 확인
7. [✅ 최종 승인] 또는 [↩️ 롤백]
```
