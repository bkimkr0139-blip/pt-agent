## 1. 시스템 개요

PPT 발표 에이전트는 **문서를 넣으면 발표용 슬라이드와 대본을 만들고, 완전히 로컬에서 돌아가는 음성으로 자동 발표까지 수행하는** 단일 웹 애플리케이션이다. 클라우드 API 의존 없이 Mac Studio 한 대에서 STT(인식)·LLM(생성)·TTS(합성) 전부를 처리하며, 발표 중 발생하는 문제를 로그에서 스스로 감지해 다음 실행에 반영하는 **무결 루프(자동 적응 폐루프)**를 갖추고 있다.

핵심 설계 원칙:

- **로컬 퍼스트** — 문서·음성·모델 전부 기기 내 처리. 외부 전송 없음.
- **무수정 보호 계층** — 결함 있는 하위 구성요소(mlx-audio 서버)를 직접 고치지 않고 프록시에서 감싸 모든 클라이언트를 보호.
- **원격 진단 가능** — 브라우저 상태를 서버 로그로 전송해 화면 없이도 발표 중 상황을 재구성할 수 있다.
- **실패는 데이터다** — 모든 실패가 사유와 함께 로그에 남고, 감시자가 읽어 자동 조정 또는 코드 패치 대기열로 적립된다.

### 4.2 발표 화면 (슬라이드 렌더링)
- **캔버스 fit + 중앙 정렬**: 덱 비율과 화면 비율이 어긋나도 슬라이드를 화면에 꽉 차게, 중앙에 렌더(positioned 도형 좌표 기반 JS 계산, `canvasMode` 그리드). [2026-10-05] 상단 여백 최소화 — 전체화면 시 topBar의 52px 예약 공간(`body.fs`로 해제)을 슬라이드에 반환, 캔버스 모드 여백 16→4px, 스택형 상단 패딩 48→14px로 슬라이드 최대 표시.
- **bbox 크롭**: 도형이 한쪽에 몰린 덱은 합영역+4% 여백으로 캔버스를 잘라내 좌표를 재매핑 — 캔버스 "안쪽" 빈 공간 제거(콘텐츠가 92% 미만일 때만, 풀블리드 덱은 무시).
- **반응형 폰트**: `container-type: size`(cqh 단위)로 캔버스 크기에 비례해 글자 축소/확대.
- 창모드/전체화면 모두 대응, 사이드패널은 닫힐 때 `visibility:hidden`으로 그림자 누수(화면 오른쪽 "프레임" 현상) 차단.
- 렌더 결과(캔버스 크기, 도형 박스 좌표)를 진단 로그에 병기 — 화면 문제를 원격으로 특정 가능.

### 4.3 발표 재생 체인
- **우선순위 TTS 큐**: 본 슬라이드 문장을 먼저 등록한 뒤 다음 슬라이드를 프리페치(선점 문제 해소), 실패 재시도와 질의응답 멘트는 큐 맨 앞 삽입.
- **긴 문장 2차 분할**: 55자 이상 문장을 쉼표 경계로 나눠 변환 대기를 흡수 — 첫 재생까지 수 분 대기하던 결함 제거.
- **조각 간 휴지 구분**: 문장 끝 700ms, 쉼표 분할 조각 200ms — "문장 중간 무음" 해소.
- **재생 감시자**: 디코딩 무반응 8초 감시(canplay 시 해제), 120초 경질 상한, 정지/일시정지 시 대기 중 타이머 즉시 해제(고아 타이머 방지).
- **오디오 잠금 해제**: 발표 시작 제스처 안에서 무음 WAV + AudioContext resume으로 브라우저 자동재생 정책 선제 차단.

### 4.4 질의응답 (QA) — [2026-10-05 전면 개편]
- 발표 중 마이크는 **기본 OFF**(설정 토글) — 배경 대화 오인로 발표가 멈추는 문제 방지. 켜면 음성 질문 → STT → LLM 답변 → 음성 응답이 발표 흐름에 끼어들며 진행. 종료 후엔 배경대화 모드로 복귀 확인 멘트.
- **3중 병렬 체인**: 질문 접수 즉시 ① 정적 추임새 프리캐시 즉시 재생(0ms) ② RAG 검색 착수(예산 2.5s, 초과 시 참조 없이 진행하고 stats.ragTimeout 기록) ③ LLM 답변 생성. 답변이 늦으면 시간벌기 추임새(프리캐시 2종)로 침묵 구간 제거. 답변 텍스트는 즉시 화면 표시, 음성은 20s 예산(초과 시 잔여 답변 큐 폐기 + 프리캐시 안내 "답변은 화면에 표시되어 있습니다" — [b0tm] 실측의 20s 침묵 제거).
- **정직 거절(센티널 판정)**: 이 임베딩은 점수로 관련/무관 구분이 불가(실측: SSOT 정답 질문 0.376 vs RBAC 무관 질문 0.374, 덱 내용 질문 0.283) → 클라이언트 점수 게이트를 두지 않고 LLM 자판단으로 전환. 참조 0건이면 LLM을 돌리지 않고 즉시 거절, 참조가 있어도 프롬프트가 "근거 없으면 다른 말 없이 정확히 `[[NO_ANSWER]]` 토큰만 출력"을 단일 지시로 강제 — 토큰이 오면 클라이언트 상수 거절 멘트(RAG_MISS_MSG, 사용자 지정 문구)로 교체. **거절 문구는 LLM이 절대 만들지 않는다.** (v10의 "답하거나 ~로 마무리" 이중 지시는 허구+면책을 둘 다 출력하는 결함으로 v10.5에서 제거.)
- **거절 → 지식 자동 습득 연동(§4.6)**: 거절과 동시에 서버에 자동 습득을 요청(백그라운드, 발표 무영향)하고 25초 후 같은 질문을 재검색해 auto 지식이 보이면 프리캐시 멘트 "추가 확인이 완료되었습니다. 다시 질문해 주세요."로 재질문을 안내.
- **멘트 프리캐시 체계(CACHED_PHRASES)**: 발표 시작 시 전 멘트를 미리 생성해 질의응답 중 재생은 0ms. 교훈 2가지가 반영됨 — ① "네," 접두는 모델 조기 EOS(프록시 REJECT→SPLIT→FAIL→캐시 영구 미스→무음)를 유발해 전부 제거 ② 긴 거절 멘트(60자) 통짜 프리페치는 절단→SPLIT 스톰(18.6s GPU 점유)을 일으켜 2구문으로 분할.
- **QA 품질 폐루프 로그(§6.7)**: 모든 질문-답변 이벤트(ragMs/scriptMs/llmMs/엔진/참조 수·top 스코어/추임새/음성 시간)를 eval/qa_log.jsonl에, 거절 질문을 eval/rag-miss.jsonl에 적재 — 다음 개선 세션과 지식 자동 습득(§4.6)의 입력.

### 4.5 발표 주석 (색연필 + 메모) — [2026-10-04]
발표 도중 슬라이드 위에 직접 표시하고, 수정할 부분/오류를 메모로 기록. 모든 기록은 폐루프 원장(integrity/annotations.jsonl)에 적립되어 관리자 페이지에서 페이지별 원본 대조로 열람.

- **색연필 드로잉**: 발표 화면 **최우측 끝 세로 레일**의 `🖍️` 토글 → 4색(빨강/파랑/노랑/초록) 선택 후 슬라이드 위에 자유 곡선. `↶` 실행취소, `🗑` 전체 지우기. 레일은 접기/펼치기 지원 — 접으면 반투명 🖍️ 핸들만 남아 발표 화면을 가리지 않고, 접힘 상태는 기억됨. 스트로크는 슬라이드 정규 좌표(0~1)로 저장 — 화면 크기와 무관하게 재현.
- **📝 메모**: 분류(슬라이드 수정/스피커노트 수정/음성 오류/기타) + 원문 인용 + 메모 본문. 스피커노트(`📜 노트`)에서 텍스트를 드래그하면 인용이 채워진 메모 창이 열림.
- **🤖 자동 기록**: TTS 실패로 브라우저 폴백 전환 시 해당 슬라이드에 음성 오류 메모가 자동 적립(슬라이드당 문장 앞부분 키로 중복 제거).
- **저장 구조**: SQLite `slide_annotations` 테이블. draw=슬라이드당 1행(재저장 시 교체), memo/auto=적립. 슬라이드 배지로 주석 존재 표시.
- **관리자 열람**: 관리자 페이지 `🖍️ 발표 주석` 패널 → PPT별 상세 페이지에서 페이지마다 ①원본(업로드 시 파싱된 스피커노트+불릿) ②주석(그리기 SVG 재현 + 메모 카드)을 나란히 대조. pptx 원본 바이너리는 보존되지 않으며 파싱 결과가 원본.
- **폐루프 연동**: annotations.jsonl 적립 → 폐루프가 음성 오류 메모(BROWSER_FALLBACK)를 감지해 client_tts_timeout 자동 상향 등에 활용 가능. 덱 자동저장 지연(최대 8초) 동안의 기록은 대기열에 쌓였다가 pptId 확정 시 일괄 전송.

### 4.6 지식 자동 습득 폐루프 (RAG 자기성장) — [2026-10-05, 사용자 요청]
"로컬 LLM에 없는 질문 → 클라우드 LLM으로 답 획득 → 자동 임베딩 → 로컬 지식화 후 답변"의 완전 자동화. 발표가 거듭될수록 자동 지식이 쌓여 로컬 답변 커버리지가 넓어진다.

```
발표 중 rag-miss 거절 → POST /api/knowledge/acquire (202 즉시 응답, 백그라운드 처리)
  → 중복/제외 확인(정규화 질문) → 클라우드 LLM(koen-openai-script, 모델 시험 주입 동일 규칙)
     · "[불확실] 표기 프로토콜": 확신 없으면 답 앞에 [불확실] → 신뢰도 0.3(그 외 0.5)
  → 질문+답변 합본 1청크 임베딩(n8n koen-openai-embed) → documents(origin='auto') 적재
  → 검색 범위에 항상 포함('⭐ 주로 참고' 스코프와 무관 — 자동 지식은 원래 덱에 없는 내용)
  → eval/knowledge.jsonl 원장 적재 + 클라이언트 25s 재확인 안내(§4.4)
  → 같은 질문 재요청 시: 일반 참조로 회수 → 로컬 LLM이 정상 답변
```

- **신뢰도 체계**: 운영자 수동 1.0(높음) / 자동 확신 0.5(보통) / 클라우드 [불확실] 0.3(낮음). 답변 프롬프트에는 자동 지식 참조에 `(자동 학습·검증 전)` **인라인 태그**만 붙인다 — 지시 문장 추가는 v10.5의 이중 지시 회귀 위험이 있어 금지.
- **중복·제외**: 같은 정규화 질문은 재습득하지 않음(문서명 `자동학습: <질문>` + in-flight 집합). 운영자가 자동 지식을 삭제하면 knowledge-dismissed.jsonl에 기록돼 재습득 대상에서 제외.
- **🧠 지식 관리 탭(관리자 콘솔)**: ① 미답변 질문(rag-miss.jsonl 최근순 유니크)에 상태 배지(대기/습득됨/제외)와 **🧠 지금 습득**/**제외** 버튼 ② 지식 리스트(수동/자동 출처 배지, 신뢰도 배지, 높음·보통·낮음 3단 즉시 조정, 삭제) ③ 수동 지식 추가(이름+내용+신뢰도 선택 → 즉시 임베딩) ④ 사이드바에 자동 지식·미답변 대기 수 배지.
- **스키마**: documents 테이블에 `origin`(manual/auto)·`confidence`(0~1) 컬럼 추가(기존 DB 1회 ALTER, 기본 manual/1.0). /api/docs·/api/search 응답에 출처·신뢰도 노출.
- **라이브 실적(배포 직후 검증)**: 실발표에서 거절됐던 "rbac가 무슨 뜻이에요"/"ssot가 무슨 뜻이에요" → 각 4.4s 습득(신뢰도 0.5) → 검색 적중 0.740/0.536(습득 전 0.374/0.376 — 질문+답변 합본 청크가 질문형 쿼리 적중률을 크게 높임) → 실물 LLM 1.1s 정상 답변(센티널 통과), 재요청 dedup 차단 확인.

### 4.7 Jev QA Router 결정 레이어 (Shadow Mode) — [2026-10-05, 지시서 적용]
RAG와 LLM 사이에 "이 질문에 답할 수 있는가"를 판단하는 결정 계층. **초기 배포는 Shadow Mode 전용** — 판단은 백그라운드 기록이고 사용자에게는 기존 QA 결과가 그대로 간다(발표 중단이 구조적으로 불가능). 판단 100건 적재 후 Canary→Active 전환 검토.

```
QA 완료(클라이언트) → POST /api/decision/observe (fire-and-forget, await 없음)
  → decision/decision_service: 판단체 실행 → 임계값 게이트(§14) → eval/decision_log.jsonl 기록
판단체(Provider 추상화): rule(로컬 규칙, 기본·즉답) / jev(설정형 엔드포인트 슬롯, 300ms 예산)
                        / llm_judge(n8n 클라우드, 롤백 타깃) — 어느 쪽이든 실패 시 exec='existing'
라우트: DIRECT(검증 지식 직답) / RAG_SHORT / RAG_LLM / LLM_REASON / NO_ANSWER / ASK_CLARIFY
```

- **규칙 판단체 설계 근거**: 절대 점수는 무관/관련을 못 가른다(v10.5 실측 — 무관 0.374 vs 관련 0.536). 그래서 규칙은 ①참조 유무 ②질문 유형(정의형/추론형/모호) ③참조 출처(auto 지식 = 그 질문을 위해 검증돼 습득된 것)를 쓰고 절대 점수는 보조로만. 섀도 축적이 휴리스틱을 실측 보정한다.
- **임계값 게이트(지시서 §14)**: DIRECT conf<0.92 → RAG_LLM 후퇴, NO_ANSWER conf<0.90 → 기존 LLM 판단(즉시 거절 안 함), RAG_SHORT conf<0.65·LLM_REASON conf<0.75 → RAG_LLM. 미달은 전부 "기존 경로".
- **오류율 정의(섀도 관찰)**: 오거절=False Reject(거절 판단했는데 실제 체인은 답변, KPI ≤5%) / 오수용=False Accept(직답 판단했는데 실제 체인은 거절, KPI ≤3%). 현재 기준선: LLM 호출률 86.7%(qa_log 15건) → 목표 ~60%(LLM -30%).
- **옵티마이저** `decision/decision_optimizer.py`: 양방향 조정 — 경질(오거절>5%→거절 문턱+0.02, 오수용>3%→직답 문턱+0.02)과 **완화**(정확도 유지 + 게이트 미달로 잃은 절감 샘플 10건+ → 문턱-0.01). 안전장치 — 표본 50건 미만 관찰만 / 키별 30분 쿨다운 / 1회 ±0.03 / 클램프(direct .85~.98, no_answer .85~.99, llm_required .60~.90) / 직전 정책 `.prev` 보관(1스텝 롤백). **LaunchAgent 로드 완료**(30분 주기, `com.wizbase.ptagent.decision-opt` → /tmp/ptagent-decision-opt.log) + 관리자 탭 "⚙️ 지금 최적화".
- **초기 실측 평가(배포일, 8질문 3-way)**: 규칙 판단 **평균 0ms** vs 실제 LLM 답변 평균 1,242ms vs LLM 판단체 평균 1.3~14s(부하 따라 변동 — 라우팅 판단을 LLM으로 하기엔 부적합, 롤백 타깃 용도만 실증). 1차 평가가 캘리브레이션 결함 포착(rbac conf 0.898<0.92 탈락, ssot 0.536<0.55 미진입 → 절감 2건 상실) → 자동지식 기준 0.50·계수 0.45로 보정 → 재평가에서 **스킵 1/8→3/8, 오수용/오거절 0건 유지**. 리포트 `eval/results/qa-jev-vs-llm-eval-*.md`.
- **보안(§31~32)**: 외부 판단체엔 질문+슬라이드 제목+RAG 점수 요약만(PPT 원문 금지), PII(전화번호/이메일/주민번호) 탐지 시 질문 마스킹 후 기록, `fields_sent` 로그.

- **라이브 검증**: 섀도 관측 2건(정상/미스 시나리오) 기록·판단 합의 확인, PII 마스킹 라이브 확인, 표본 부족 시 조정 없음 확인, 배터리 60/60.

### 5.1 TTS 프록시 방어 계층 (:8321) — 시스템의 심장

mlx-audio 서버(0.4.5/0.5.7)의 두 근본 결함을 **프록시에서 무수정 방어**:

1. **동시 요청 GPU 경합** → 무한 행/96초 무음. 프록시가 전역 락으로 업스트림 생성을 엄격 직렬화(스트리밍 본문을 락 안에서 완전 소비).
2. **EOS 토큰 미생성** → 스토캐스틱하게 조기 종료(반 단어 0.8초) 또는 과잉 생성(runaway). 같은 문장이 temp 무관 ~87% 실패(502/502/200 실측) — 토큰 스트림을 아예 바꾸는 분할이 유일한 회피책.

요청 하나가 통과하는 전 경로:

```
입력 → 문장 분할([.!?…] 경계, 4자 미만 조각은 병합)
  └─ 각 문장: max_tokens 상한(자×2.8+100)으로 생성 시간 묶기
       ├─ 재시도 N회(정책 attempts, 온도 사다리 0.3→0.15)
       ├─ 길이 게이트: trim 후 cap 초과=runaway 재시도 / floor 미달=truncated 재시도
       │    · trailing 무음 절단(trim_tail_silence) — EOS 실패가 붙이는 수 초 무음 제거
       │    · floor = [v10] 종결문(.!?~끝) max(0.45, 자×0.11+0.22) / 소프트(쉼표 등) max(0.45, 자×0.08+0.25)초
       │      — 종결문의 절단 밴드(≥9.1자/초)까지 포착(1,415조각 실측 기반). floor_mult 정책 배율은
       │        소프트 열거 조각까지 걸러 SPLIT 스톰을 내므로 미사용 — 프록시 코드로 시행
       │    · cap   = max(8.0, 자×0.28+3.0)초 — 무음/garbage runaway 절단
       └─ 전부 실패 시: ①열거 접미사 재작성('첫째,'→'첫 번째,' — 동일 지점 EOS 사망 실측 방어)
             ②조각 2분할(depth 1까지 재귀, 토큰 스트림 교체 목적):
               쉼표·가운뎃점 중앙 근접 → 없으면 공백 → 한쪽 3자 미만이거나 없으면 문자 중앙 강제 절단(6자+)
       → 성공 조각들을 RIFF 청크 파싱으로 PCM 병합해 단일 WAV 반환 (클라이언트 무수정)
       → 최종 실패만 502 JSON(사유 포함) — 클라이언트가 폴백 판단
```

**[2026-10-05 v11] 클라이언트 단절 취소 (19:08 고장 방어).** 프록시 EOS 재시도 사슬(REJECT→SPLIT
반복, 실측 44.5s) 도중 클라이언트가 먼저 포기해도 uvicorn은 핸들러를 취소하지 않아 좀비 생성이
GEN_LOCK을 계속 잡고 있었다 → 뒤이은 Q&A 음성이 프록시에서 다시 같은 시간을 대기(클라이언트 큐만
비워도 소용없는 2차 병목). 대책: ①`speech()`가 0.3s 폴링 감시자로 클라이언트 단절을 감지해
`ClientGone` — 사슬 전체 즉시 언와인드 + 업스트림 httpx 요청 취소 ②업스트림 mlx-audio는

### 5.2 클라이언트 TTS 직렬 큐 (ppt-agent.html)

## 6. 무결 루프 (폐루프) — 자동 적응 시스템

### 6.1 목적
"로깅하다가 발표 이슈가 생길 때마다 다음번 실행에는 자동으로 patch" — 발표를 돌릴수록 시스템이 스스로 튜닝되어 **점점 무결한 상태로 수렴**하는 것을 목표로 한다. 사람의 개입은 코드 레벨 결함이 적립될 때만 필요하다.

### 6.2 구성요소

| 파일 | 역할 |
|---|---|
| `works/pt-agent/integrity_watch.py` | 감시자. 5분마다 로그 증분 스캔 → 분류 → 자동조정/적립 (stdlib 전용) |
| `works/bc-ai/tts_policy.json` | 정책 단일 진실원. 버전/갱신이력/클램프 포함 |
| `works/pt-agent/integrity/issues.jsonl` | 코드 패치 대기열. 다음 Claude 세션이 읽고 패치 |
| `works/pt-agent/integrity/status.json` | 최근 스캔 결과(이슈 카운트·통계·자동조정 내역) |
| `works/pt-agent/integrity/checkpoints.json` | 로그 이어읽기 오프셋(증분 스캔) |

### 6.3 데이터 흐름

```
발표 실행 → pt-agent.log([클라이언트 진단]) + mlx-tts-proxy.log(REQ/OK/REJECT/SPLIT/FAIL+사유)
   │
integrity_watch (5분)
   ├─ 매개변수형(auto) → tts_policy.json 자동 조정 (version++, updated_by=integrity_watch)
   │      프록시: 요청마다 mtime 감지 재로드 → "POLICY vN 로드" (재시작 불필요)
   │      클라이언트: 로드 시 /ppt-agent/api/tts-policy 수신 (TTS 타임아웃 20~90s 클램프)
   └─ 코드형(code) → issues.jsonl에 증거+설명 적립 → 다음 Claude 세션이 코드 패치
```

### 6.5 자동 패치 규칙 (안전장치 포함)

| 조건 | 조정 | 클램프 |
|---|---|---|
| FAIL-FINAL 또는 브라우저 폴백 발생 | 재시도 `attempts` +1 | 1~3 |
| RUNAWAY 3건 이상 | 길이 상한 `cap_mult` ×1.08 | 0.7~1.2 |
| 브라우저 폴백 2건 이상(클라이언트 타임아웃 중단 포함) | 클라이언트 TTS 타임아웃 ×1.25 | 20~90초 |

- **이중 클램프**: 정책 파일의 `clamps` + 프록시 내부 `_CLAMP` — 어떤 경로로라도 폭주 불가.
- **30분 쿨다운**: 같은 이슈 코드에 대한 재조정은 30분 간격.
- **전부 감사 가능**: 모든 조정은 `from→to`와 함께 status.json/issues.jsonl에 기록.
- 최초 가동 실적: 역대 로그의 FAIL-FINAL 4건을 근거로 attempts 2→3 자동 패치(정책 v2), 누적 116건 성공/8건 분할 구출 통계 확보.

## 7. 모델 교체 평가 모듈 (관리자 전용)

관리자 메뉴의 "🔄 모델 교체 평가"에서 로컬 LLM·STT·TTS의 더 나은 모델을 조사하고, 실측으로 비교하고, 실제 트래픽 시험을 거쳐 교체 여부를 판단하는 5단계 파이프라인. **시스템 기능 구성상 모델 생애주기 관리 계층**으로, 무결 루프(§6)가 모델 "내부" 품질을 자동 보정하는 동안 이 모듈이 모델 "바깥"(어떤 모델을 쓸 것인가)을 관리한다.

```
1단계 조사(HuggingFace 최신날짜순) → 2단계 벤치마크(전부 실측) → 3단계 비교 차트·자동 판정
   → 4단계 시험 운영(실제 발표 트래픽 전환) → 5단계 무결루프 검증 → ✅ 최종 승인 / ↩️ 롤백
```

### 7.1 구성 (전체 기능 구성 내 위치)

| 구성요소 | 역할 |
|---|---|
| `model_eval.js` | 평가 엔진 — 조사·벤치마크 실행기·판정·시험 전환·검증 보고서 집계 |
| `eval_page.js` | 평가 페이지 UI — 관리자 페이지에서 진입 |
| `eval/registry.json` | 스택별 현재 모델 단일 진실원 (승인 시 갱신) |
| `eval/discovery.json` | 조사 캐시(30분) · `eval/trial.json` 시험 상태·백업 · `eval/results/` 실측 리포트 보관 |
| 전환 연동 지점 | server.js(LLM model 주입) · tts_policy.json+프록시(TTS 강제) — §6 무결 루프와 같은 정책 파일 공유 |

상세 설계·특장점·타 시스템 적용방안은 전용 문서 `docs/model-eval.md`(평가 화면 우측 상단 "📄 평가 시스템 문서"에서 다운로드, 상태 스냅샷 부록 자동 첨부) 참조.

### 7.2 단계별 기능

- **조사**: HF API를 스택별 질의 세트(LLM=gguf 필터, STT, TTS)로 **최신날짜순** 조회, 다운로드 10+ 필터로 잡동사니 제거, 30분 캐시. 각 후보 행에 모델명·태그에서 자동 추출한 **특징**(파라미터·양자화·계열·MLX/ONNX·증류·검열제거⚠), **시장 피드백**(다운로드/좋아요 → 🟢검증됨/🔵주목/⚪신규), **기대 개선(추정)** 컬럼을 채워 선택 판단을 돕는다(추정이며 실측 근거는 벤치마크).
- **벤치마크(실측)**:
  - LLM — 발표 도메인 5개 태스크(대본 생성·근거 QA·지시 이행·**언어 올바름**·요약) × 현재/후보 스트리밍 실측: TTFT, tok/s, 한국어 비율(문자 기준 분모), 중국어 오염 검사, 길이 적정성. **언어 올바름 실패 시 무조건 "비권장"**(qwen2.5:14b의 중국어 답변 결함 클래스 방어).
  - STT — bench 샘플 A/B(8323 Qwen3-ASR vs 8782 whisper): RTF·처리시간·빈 결과 수.
  - TTS — 5문장 프록시 경유 실측: 성공률·지연·자연 길이 비율(4~7자/초).
- **차트**: 현재 vs 후보 **div 기반 쌍봉 차트**(SVG 텍스트 좌우 왜곡 문제 수정) + 변화율 배지("낮을수록 좋은" 지표 방향 자동 보정), 사용자 관점 요약 불릿, 자동 판정(교체 권장/시험 권장/보류/비권장).
- **시험 운영 전환 메커니즘**:
  - LLM — server.js가 `eval/trial.json`(status=trial)을 읽어 body.model을 n8n 프록시에 주입. n8n 게이트웨이가 b.model을 존중하므로 n8n·클라이언트 무수정.
  - TTS — `tts_policy.json`에 tts_model/tts_voice 기록 → 프록시가 모든 요청에 강제 적용(mtime 즉시 반영, 롤백 즉시 복원, 클라이언트 무수정).
  - STT — 자동 전환 없음(발표 QA는 브라우저 Web Speech API, 8323은 n8n 서비스용). 전환은 n8n koen_local_stt 워크플로우 대상 수동 변경.
- **검증 보고서(무결루프 연동)**: 시험창 vs 직전 동일 길이 창의 실제 트래픽 비교 — 문장 성공 수·평균 생성시간·분할 자동 구출·최종 실패(TTS, 프록시 로그), 호출 수·평균 응답시간·오류(LLM, 서버 접근 로그), 시험 중 무결루프가 잡은 이슈(integrity/issues.jsonl). 벤치마크 수치가 아닌 **운영 데이터로만** 최종 판단.
- **최종 승인**: registry 갱신 + 전환 유지. **롤백**: 백업 정책 즉시 복원.

주의: 벤치마크는 실제 GPU를 점유하므로 **발표 중 실행 금지**(오염 경고가 UI에 표시됨). LLM 후보는 `ollama pull` 사전 설치 필요. TTS 후보 첫 생성 시 HF 다운로드가 발생할 수 있음.

## 8. 진단 및 로그

- **클라이언트 진단 비콘(dbg)**: 브라우저의 TTS 요청/재생 시작·종료/차단/폴백/슬라이드 전환/렌더 좌표를 배치 전송 → `pt-agent.log`에 `[클라이언트 진단]` 행으로 기록, 페이지 경과시간(+X.Xs) 부착. 화면 콘솔은 숨겨져 있고 `?dbg=1`로 옵트인.
- **프록시 로그**: 타임스탬프 + REQ/OK/REJECT/FAIL/SPLIT/SPLIT-OK/FAIL-FINAL/POLICY 행 — 실패 경로의 각 단계가 사유와 함께 남는다.

| 로그 | 위치 |
|---|---|
| 서버 접근+클라이언트 진단 | `works/pt-agent/pt-agent.log` |
| TTS 프록시 | `works/bc-ai/mlx-tts-proxy.log` |
| 무결 감시자 | `works/pt-agent/integrity/watch.log` |
| QA·지식 폐루프 원장 | `works/pt-agent/eval/*.jsonl` (§6.7) |
| 결정 레이어 | `works/pt-agent/eval/decision_log.jsonl` · `decision_status.json` (§4.7) |

**장애 해석 가이드**: "폴백 후 재생 이벤트 소실"은 대부분 사용자 정지(버그 아님) · `REJECT truncated` 다발은 스토캐스틱 EOS — SPLIT-OK가 뒤따르면 정상 복구 · `FAIL-FINAL`에 SPLIT 라인이 없으면 분할 지점 없는 붙은 텍스트(문자 강제 절단이 담당) · 외부 IP 요청이 계속 찍히면 브라우저가 살아있는 것.

## 11. 알려진 제약

- TTS는 직렬 처리(결함 방어) — 동시 다발 요청 시 대기 발생. 발표 체인은 단일 스트림이라 영향 없음.
- 스토캐스틱 EOS 실패는 근절이 아니라 **회피**(분할로 토큰 스트림 교체) — 드물게 최종 실패가 남으면 브라우저 폴백이 받는다(무결 루프가 재시도 상향으로 흡수).
- 발표 중 LLM 스크립트 생성과 TTS가 GPU를 경합하면 truncation 빈도가 올라가는 경향(추정) — 무결 루프가 이를 길이 게이트 배율로 흡수.
- 1.7B CustomVoice TTS는 장기 grind 생성에서 **확률적 화자 이탈**(순간 목소리 변화)이 잔존한다(v10.1 클래스, 온도 무관 실측) — 멘트 분할·프리페치 스톰 제거로 빈도만 낮춘 상태. 재발 시 해당 조각의 프록시 elapsed와 짝지어 관찰.
- 지식 자동 습득은 클라우드 LLM(n8n koen-openai-script) 의존 — 오프라인/장애 시 습득만 실패하고 거절 응답·발표는 정상 동작. 자동 습득 신뢰도 0.3([불확실]) 지식은 관리 콘솔에서 검토 후 신뢰도를 조정할 것.
- 결정 레이어(§4.7)는 Shadow Mode 단계 — 판단·기록·보정만 하고 QA 결과에 개입하지 않는다. Canary/Active 전환은 ①판단 100건+ ②오거절 ≤5%·오수용 ≤3% 확인 후 decision_policy.json 모드 전환으로 하며, 클라이언트의 라우트 실행 계획 수행 코드는 그때 별도 적용한다. 옵티마이저 LaunchAgent(30분) 로드 완료 — 로그 /tmp/ptagent-decision-opt.log.
- n8n 워크플로우 DB 직접 수정 시 `workflow_entity.nodes`와 `workflow_history.nodes`(activeVersionId 행)를 함께 수정해야 함.
